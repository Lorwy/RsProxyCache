# 首版播放验收

使用可控测试源站记录每次回源的请求范围、次数和响应体字节数。

- 清空缓存后，直接请求单文件视频中间的字节区间，验证服务按需回源并返回正确的 `206` 和字节内容。部分命中时，记录的回源响应体字节数应等于缺口大小。
- 重复请求同一区间，验证回源次数保持不变。重启代理后再次请求，验证仍然命中。
- 在同一源地址替换视频并更新强 `ETag`，构造需要补齐缺口的请求，验证响应只包含新版本字节。模拟检测到换片之后的重取失败，验证后续请求不会继续命中已失效的旧区间。
- 并发发送两个范围不同的播放请求，使它们共享同一缺口，验证缺口只回源一次。
- 调小容量上限，访问多个区间后触发淘汰，验证优先腾出最久未使用区间占用的空间。

使用至少一个实际要接入的播放器，打开直接拼接的 `/v1/https://…` 地址，验证能起播并拖动进度条。检查代理收到的路径和查询串，确认双斜杠、签名参数顺序和百分号编码得到保留。目标播放器在实际接入时确定。

## FFmpeg 跨版本验收

HLS 回归会对比原始本地文件、代理播放和发布后的离线文件在第 4 秒起的帧哈希。MPEG-TS 始终执行输入跳转。若 FFmpeg 对原始本地 fMP4 就无法完成输入跳转，例如 Linux 上的 FFmpeg 5.1，则同一用例改为解码后从第 4 秒取帧，并检查目标分片确实经过代理。Media3 的播放位置推进单独验收。

## 离线下载并发基线

使用 release 构建，在本机回环源站对比空闲代理和同时运行两个离线下载任务的代理。

```sh
cargo build --locked --release
RPC_TEST_BINARY=target/release/rs-proxy-cache python3 tests/offline_benchmark.py --samples 10
```

每次采样使用独立缓存目录。两个模式交替执行，分别记录 FFmpeg 冷启动和从 9 秒位置打开到成功解码一帧的用时，同时采样代理 RSS、缓存目录文件总字节数和源站并发 GET 峰值。时间包含 FFmpeg 子进程启动和退出，跳转指标使用独立冷缓存。这组指标适合复查主机端回归，Android Media3 使用设备日志单独验收。

## 磁盘写满恢复

本地验收在独立的 32 MiB 临时卷上制造实际的 `ENOSPC`。用例验证离线任务报告 `disk_full`、在线播放仍可读完，以及释放空间后能重新下载并发布。本地如已有专用小容量挂载卷，可用 `RPC_TEST_DISK_FULL_ROOT` 指定挂载点，再运行 `PlaybackTests.test_offline_reports_real_disk_full_and_retries`。测试会填满该临时卷，并在退出时删除测试目录。

## Android 发布候选

在本地运行 `sh tests/verify.sh --full`。播放回归通过后，按 SDK 文档构建四种 ABI 的 Android AAR，并记录对应源码版本和产物 SHA-256。用同一 AAR 构建 Media3 验收 APK，记录 APK SHA-256、设备型号、系统版本和 `RpcAcceptance` 日志。MP4 与明文 HLS 分别执行下载、取消续补、断网强停冷启动、首帧及中点跳转后续播，确认两轮彼此使用独立的 `cacheRun`。
